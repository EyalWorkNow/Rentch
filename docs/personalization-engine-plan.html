✅ בוצע — Phase 0 מומש, מנוע Phase 1 בנוי (רדום)

Phase 0 הושלם: 4 מוקשי-הלוגים תוקנו (feature-parity rankFeatures · נרמול-dwell · impressions בפיד · שונות-מיקום) + ε-greedy + A/B (variantFor). מנוע Phase 1 בנוי ומאומת מקצה-לקצה: ml/train.py (LightGBM) → model.json → model_scorer.mjs בתוך ה-Node Lambda (blend α·linear+model, treatment bucket) — הוכח חי: good 0.63 > bad 0.41. פרוס רדום (אין מודל → pure-linear ללא שינוי); הדלקה בפקודה activate.sh כשיהיו ≥200 שורות מתויגות. Phase 2-3 עתידיים, מגודרים בנפח. נאמן להכרעת המבקר — בלי Fargate/MLflow/Prefect.

01 ההכרעה של הפאנל

שני הארכיטקטים תיארו מערכת ML מצוינת — ומכוונת לרג'ים דאטה שאנחנו במרחק שנות-תנועה ממנו. המבקר הראה שרוב הרכיבים כבר קיימים בקוד (שער eligibility, ציון implicit מדורג, item-item CF, צינור ייצוא אימון, לומד GBDT/FTRL על המכשיר). המערכת לא חסרה מודל — חסרה לה דאטה, ושני דברים זולים שהופכים את הדאטה הבאה לאמינה: שלמות לוגים + מנוע אקספלורציה (ε-greedy). נשארים Lambda-only, scale-to-zero. לא מקימים Fargate/MLflow/Prefect/GrowthBook עכשיו.

02 הארכיטקטורה: retrieval → rank → explore

העיקרון התעשייתי (YouTube 2016, two-tower 2019): שלב אחזור זול עם recall גבוה, ואז דירוג יקר ומדויק. אצלנו האחזור הוא לא-בעיה (הקטלוג נכנס לזיכרון) — כל המנוף ב-ranker + אקספלורציה.

03 ה-Stack: מה לבנות עכשיו מול מה לדחות

המלצת מומחה ה-open-source, מסוננת דרך המבקר. הכלל: managed או Lambda-only — כל שירות self-hosted הוא משהו שמצלצל ב-3 לפנות בוקר בלי ערך מוצר עכשיו.

שכבההכרעהמה, ולמה
RankerבנהLightGBM (MIT) — LambdaMART, מהיר, tabular. משרתים אותו בתוך ה-Node Lambda הקיים (עצים = כמה KB, מוערך ב-JS). בלי Fargate.
אחזור CFקייםitem-item co-engagement כבר רץ (/reco/cf). iALS (implicit) רק כשתהיה צפיפות — nightly batch, לא בזמן אמת.
אקספלורציהבנהε-greedy בשירות — כמה שורות. מייצר את הדאטה שהכל תלוי בה. Vowpal Wabbit / Thompson — דחייה.
Offline storeמינימליdump יומי של search-log ל-S3 (EventBridge→Lambda). /ml/export כבר עושה את ה-join. Parquet+DuckDB — כשה-scan יגדל.
אימוןקרון פשוטGitHub Actions cron מריץ Python (LightGBM) על ה-dump. Prefect/Airflow/Dagster — לא. DAG של צעד אחד לא צריך שרת אורקסטרציה.
Registryחתוךמודל = JSON ב-S3 + git SHA. MLflow הוא שרת לתחזק עבור מודל אחד. מיותר.
A/Bhashhash(userId)%buckets ב-router, וריאנט מוטבע ב-rently-events. GrowthBook self-hosted — לא (שרת+Postgres). managed free-tier אם צריך UI.
Serving infraחתוך עכשיוFargate always-on = NAT gateway ~$32/חודש + burn 24/7 לאפס-משתמשים + hop רשת נוסף על נתיב הדירוג (זיכרון-latency כבר סימן את זה). ל-Lambda container image לפני Fargate.
Vector DB / two-tower / streamsחתוךKafka/Flink/Feast/Qdrant/TorchRec — כולם התשובה של צוות-ענק לבעיה שאין לנו. DynamoDB Streams מיותר: /interactions כבר עושה read-modify-write inline.

04 האלגוריתם: לזקק התנהגות לתווית

היתרון שלנו הוא עושר-הסיגנל — אז הנדסת התוויות חשובה יותר מבחירת המודל. מבוסס על עשרות מאמרים (מקורות למטה), מגודר לפי נפח הדאטה שכל שיטה דורשת.

טכניקהמתיהמהות + הסיכון אצלנו
Dwell כתווית מדורגת (Yi 2014)עכשיושהייה = פרוקסי חזק לעניין. אבל מוטה לפי אורך (דירה עם 40 תמונות מרוויחה dwell) — צריך לנרמל מול כמות-מדיה/אורך-תיאור. היתרון שלנו, אם נתקן את ההטיה.
שליליים מהתנהגות (BPR 2009)עכשיוbounce מהיר/back-click = שלילי חזק; pass = שלילי בינוני; לא-נצפה ≠ שלילי. הטעות הכי נפוצה — ולוגי ה-impression שלנו מאפשרים לתקן.
LambdaMART (Burges 2010)~10kה-ranker. דורש אלפי impressions מדורגים + שונות-מיקום. הדירוג הנוכחי דטרמיניסטי → tree ילמד "תסמוך על ה-rank הקיים" ויינעל feedback-loop. קודם אקספלורציה.
מטרה מרובה: engage מול lead (ESMM 2018)בהמשךp(lead)=p(engage)·p(lead|engage) מתקן sample-bias של יעד דליל. עכשיו: scalarization פשוט w·p(lead)+…−w·bounce.
כיול ל-p(lead) (Platt)דורש lead-יםאי אפשר לכייל להמרה שלא נצפתה. עד אז — הציון הוא מפתח-מיון, לא הסתברות (וזה בסדר).
Thompson / LinUCB priors (Chapelle 2011)אחרי εבנדיט מנצל cohort/persona כ-prior לקר-סטארט. אבל TS מלא כבד מדי לפני תנועה — ε-greedy נותן את אותה דאטה בשבריר מהמורכבות.
Debiasing מיקום (PAL 2019 / IPS 2017)דורש ε-logsדורש propensities מאקספלורציה אקראית — שאנחנו עוד לא מייצרים. chicken-and-egg: קודם ε-greedy.
iALS latent-affinity (Hu 2008)דורש צפיפותconfidence c=1+α·signal ממפה בול לציון ה-implicit שלנו. אבל לא פותר cold-start ולא-דירה חדשה — פיצ'ר, לא ה-ranker.
two-tower / SASRec / MMoEדלגקטלוג מתחלף, סשנים קצרים, funnel סופי, IDs לא יציבים. דורש 10⁶–10⁷ אירועים. מסלול-בוגר, לא עכשיו.

05 ארבעה מוקשי-נכונות לתקן לפני הכל

✅ כל הארבעה תוקנו ב-Phase 0. המבקר תפס אותם בקוד; בלעדיהם כל מודל עתידי היה לומד זבל בשקט — עכשיו הם סגורים.

Feature skew

יש 3 מרחבי-פיצ'רים שונים (on-device ~15 מימד, rankSignals בשרת 7, blob של /search/log). מודל חייב לרוץ על הפיצ'רים שאומן עליהם.

✔ לוג את rankSignals של השרת עצמו כפיצ'רי ה-impression

שליליים = לא-מלוגים

trainingRowsFrom מתייג כל impression בלי outcome כ-0 — אבל הפיד הראשי לא תמיד פולט outcome, אז "נצפה-ונדחה" ו"מעולם-לא-נראה" קורסים ל-0 אחד.

✔ פלוט impression+outcome בפיד הראשי; הבחן נראה/לא-נראה

אין נרמול-dwell

שורת ה-implicit לא שומרת כמות-מדיה/אורך-תיאור, אז אי אפשר לנרמל את ה-dwell מול "גודל" הדירה. ההטיה נכנסת לתווית.

✔ הוסף media-count + desc-length לשורת interaction

הטיית-מיקום בלתי-ניתנת-לתיקון

הדירוג דטרמיניסטי → rank ≈ f(score). אין שונות לתקן מולה, וכל מודל פשוט ישכתב את המשקלים הליניאריים הקיימים.

✔ הפעל ε-greedy — הוא מייצר את השונות

06 מפת הדרך — מגודרת בטריגרים

מקסום למידה-לכל-מאמץ, שצוות קטן באמת יכול לתחזק. מפורש לגבי מה לא לבנות עדיין.

PHASE 0 ✅

בוצע · pre-launch

הושלם: 4 מוקשי-לוגים + ε-greedy + A/B — הקרקע מוכנה
  • לשמור את ה-ranker הליניארי לפי cohort כ-prior + את ה-GBDT/FTRL על המכשיר לקר-סטארט
  • לתקן את 4 מוקשי-הלוגים (סעיף 05) — ה-ROI הכי גבוה בכל התוכנית
  • להוסיף ε-greedy על ה-top-N ולתייג את ביט-האקספלורציה — מייצר דאטה בלתי-מוטה
  • A/B = hash ב-router. Offline = dump יומי ל-S3. בלי שרתים חדשים
PHASE 1 ⚙︎

מודל ראשון · בנוי · רדום

הצינור מוכן (train.py+scorer+activate.sh); נדלק ב-טריגר: ≥200 שורות מתויגות
  • לאמן LightGBM logistic (לא LambdaMART עדיין) offline ב-cron
  • לשרת אותו בתוך ה-Node Lambda — עצים ל-JSON, הערכה ב-JS. בלי Fargate/ONNX
  • לשלב, לא להחליף: score = α·linear + (1−α)·model, α יורד ככל שהדאטה גדל
PHASE 2

דירוג נלמד מלא

טריגר: עשרות אלפי impressions מדורגים + שונות-מיקום אמיתית
  • שדרוג ל-LambdaMART עם תוויות מדורגות (שימוש חוזר בסולם implicitScore)
  • Debiasing מיקום (PAL/IPS) — עכשיו יש ε-logs להערכת propensities
  • מטרה-מרובה scalar; ESMM/MMoE רק אם ה-scalar מפגר. iALS nightly אם CF לא מספיק
PHASE 3

סקייל

טריגר: latency/throughput/גודל-קטלוג נמדדים ככואבים בפועל
  • משטח-serving ייעודי (Lambda container לפני Fargate), vector index אם brute-force ה-kNN מאט
  • Thompson Sampling אם ה-regret של ε-greedy עולה כסף; feature store אמיתי אם skew נמשך
  • לא לבנות עד טריגר: Kafka, Flink, Feast, MLflow, Prefect, GrowthBook self-hosted, two-tower, MMoE
